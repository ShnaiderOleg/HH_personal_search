# HHSearch — контекст проекта

## Назначение

HHSearch — личный проект для автоматизации поиска работы владельца проекта. Сервис собирает вакансии hh.ru, сохраняет их, помогает фильтровать и оценивать результаты, отслеживать статусы и получать уведомления.

Проект не является публичным продуктом, не предназначен для других пользователей и не требует командных процессов разработки.

## Владелец и разработка

- Владелец и единственный пользователь проекта — автор проекта.
- Разработка ведется одним человеком.
- Все изменения кода выполняются только через Codex.
- Codex должен учитывать этот файл и `TASK.MD` перед началом изменений.
- После каждого законченного блока изменений Codex самостоятельно выполняет доступные проверки и тесты.
- После успешной проверки Codex кратко сообщает результат и предлагает создать коммит и выполнить push.
- Коммит и push выполняются только после явного согласия владельца.

## Среды

### Development и test

- Среда: текущий компьютер владельца, Windows.
- Рабочая копия: папка проекта HHSearch.
- Development и test используют одну локальную среду.
- Локальный адрес приложения: `http://127.0.0.1:8000`.
- Локальные данные и `.env` не считаются продакшн-данными.

### Production

- Сервер: `192.168.1.88`.
- ОС: Debian Linux.
- Адрес приложения: `http://192.168.1.88:8010`.
- HTTPS сейчас не используется.
- Деплой выполняется владельцем вручную.
- Источник деплоя: основная ветка `main` GitHub-репозитория.
- Codex не выполняет деплой на production без отдельного прямого поручения.

## Репозиторий и выпуск изменений

- Основная ветка: `main`.
- В `main` должны попадать только проверенные изменения.
- Обычный цикл работы:
  1. Проверить `PROJECT.MD`, `TASK.MD` и состояние Git.
  2. Выполнить один логически завершенный блок изменений локально.
  3. Запустить автоматические тесты и необходимые проверки интерфейса/API.
  4. Сообщить, что изменено и что проверено.
  5. Предложить коммит и push.
  6. После согласия владельца создать коммит и отправить его в `origin/main`.
  7. Владелец вручную обновляет production из `main` и перезапускает сервис.

Автоматический деплой и отдельная staging-среда сейчас не требуются.

## Технологии

- Python и FastAPI.
- Jinja2, JavaScript и CSS.
- SQLAlchemy и SQLite.
- APScheduler.
- Парсинг веб-выдачи hh.ru.
- Telegram/email-уведомления и опциональная AI-оценка вакансий.

## Обязательные проверки

Минимум после каждого блока изменений:

```powershell
git diff --check
.venv-runtime\Scripts\python.exe -m pytest -q
```

Дополнительно, в зависимости от изменений:

- для UI: проверить `/`, `/searches`, `/vacancies` и мобильные ширины;
- для API: проверить измененные endpoint и негативные сценарии;
- для БД: проверить миграцию на копии базы и сохранность данных;
- для парсера: проверить тестовые HTML-примеры, не увеличивая нагрузку на hh.ru;
- для production-инструкций: использовать команды Debian/systemd и адрес порта `8010`.

Если проверку выполнить невозможно, Codex должен явно указать, что именно не проверено и почему.

## Данные и безопасность

- Токены, cookies, API-ключи и пароли хранятся только в `.env`.
- Секреты запрещено добавлять в Git, код, документацию, логи и сообщения.
- `.venv`, `.venv-runtime`, временные файлы и локальные логи не коммитятся.
- Перед изменением схемы или потенциально опасной операцией с SQLite создается резервная копия базы.
- Локальная и production-базы считаются разными наборами данных.
- Удаление данных и изменение production выполняются только по прямому поручению владельца.

## Ограничения и риски

- Парсинг веб-интерфейса hh.ru может противоречить условиям использования и привести к блокировке.
- Разметка hh.ru может измениться и сломать парсер.
- Частоту запросов нельзя увеличивать без оценки риска блокировки.
- Статические файлы браузер может кэшировать; для CSS и JavaScript требуется версионирование URL.
- Production работает по HTTP внутри локальной сети.

## Критерий готовности изменения

Изменение считается готовым к предложению коммита, если:

- задача выполнена в заявленном объеме;
- отсутствуют случайные изменения и секреты;
- `git diff --check` проходит;
- релевантные автоматические тесты проходят;
- выполнена доступная функциональная проверка;
- известные ограничения и непроверенные части явно перечислены.
